# Research Rover — New Features

**Date:** 2026-05-29
**Baseline:** changes since the last pushed commit `125bb06` ("chat,search,embeddings,chat-ui -- done")
**Scope:** Embedding-creation pipeline (backend service + API) and the embedding UI (Chat page, shared progress modal, API client).

All four features below relate to how vector embeddings are generated from a CSV of research papers. Together they make embedding creation **faster**, **optional in depth**, **re-runnable**, and **interruptible**.

---

## Summary

| # | Feature | Benefit |
|---|---------|---------|
| 1 | Parallel full-text scraping | Embedding creation is dramatically faster |
| 2 | Optional / capped full-text scraping | "Abstracts-only" fast mode; tunable scraping |
| 3 | Recreate (force-rebuild) embeddings | Upgrade an existing index instead of being locked in |
| 4 | Cancel an in-progress embedding job | Stop a long run without restarting the server |

## 1. Parallel Full-Text Scraping (Performance)

**Problem.** Creating embeddings was slow. The first stage of the pipeline downloads the full text of each paper from its URL. Previously this was done **one paper at a time**, and the code waited a fixed **one second after every single paper** out of politeness to servers. For a few hundred papers this added minutes of mostly idle waiting before any embedding work began.

**What changed.** The full-text extraction stage now fetches paper URLs **concurrently** instead of sequentially:

- The fixed one-second-per-paper delay was removed entirely.
- Downloads run in parallel, bounded by a configurable concurrency limit (default 10 simultaneous fetches).
- **Per-domain politeness is preserved without a global delay:** the system never sends more than one request to the same website host at a time, while still fetching from *different* publishers in parallel.
- A single reusable HTTP session is used (connection pooling), and progress is reported as each download completes.

**Result.** The dominant cost of embedding creation (the scraping stage) drops from minutes to seconds for typical result sets, with no change to the text that gets extracted — only how it is fetched.

**Files:** `backend/app/services/embedding_service.py` (`extract_full_text_to_json` rewritten).

## 2. Optional & Capped Full-Text Scraping (Speed/Quality Control)

**Problem.** Full-text scraping is the slow part, but it is not always needed — the paper abstracts alone are often enough to chat with. There was no way to skip scraping or limit how much of it happened.

**What changed.** Scraping is now a controllable option:

- **Abstracts-only ("fast") mode:** when scraping is turned off, the pipeline skips the network entirely and builds embeddings from abstracts. This stage becomes near-instant.
- **Cap on scraping:** an optional limit on how many paper URLs to scrape.
- These are exposed both as **server defaults** (settings) and as **per-request overrides** sent from the UI.

**User-facing.** The Chat page's collection panel now has a checkbox:

> **Scrape full text from paper URLs** — *(richer answers, slower)* / *(abstracts only, fast)*

Leaving it checked keeps the original full-text behaviour (the default). Unchecking it produces a fast, abstracts-only index.

**Files:**
- `backend/app/core/config.py` — new settings: `SCRAPE_FULL_TEXT`, `SCRAPE_CONCURRENCY`, `SCRAPE_TIMEOUT`, `SCRAPE_MAX_PAPERS`.
- `backend/app/models/schemas.py` — new `EmbeddingOptions` request model (`scrape_full_text`, `max_scrape`).
- `backend/app/api/routes/embeddings.py` — resolves per-request options over settings defaults.
- `backend/app/services/embedding_service.py` — abstracts-only fast path; honours the cap.
- `frontend/src/services/api.ts` — `EmbeddingOptions` interface; `create()` now sends options.
- `frontend/src/context/EmbeddingContext.tsx` — app-wide `scrapeFullText` toggle state.
- `frontend/src/pages/ChatPage.tsx` — the scraping checkbox.

## 3. Recreate (Force-Rebuild) Embeddings

**Problem.** Once embeddings existed for a file, the system refused to rebuild them — the API returned "Embeddings already exist" and the button was disabled. This meant you could not, for example, upgrade a fast abstracts-only index into a full-text one without manually deleting files.

**What changed.** Embeddings can now be **rebuilt on demand**:

- A `force` option bypasses the "already exists" check and overwrites the existing index.
- On the Chat page, when an index already exists the button now reads **"Recreate embeddings"** (enabled) instead of a disabled "Embeddings ready". Clicking it rebuilds using the **current** scraping setting.

**Typical workflow this unlocks:**
1. Create a fast abstracts-only index and start chatting.
2. Later, tick "Scrape full text" and click **Recreate embeddings** to upgrade the same file to a richer full-text index.

**Files:**
- `backend/app/models/schemas.py` — `force` field on `EmbeddingOptions`.
- `backend/app/api/routes/embeddings.py` — existence check skipped when `force` is set.
- `frontend/src/services/api.ts` — `force` in `EmbeddingOptions`.
- `frontend/src/context/EmbeddingContext.tsx` — `startEmbeddings(filename, force?)`.
- `frontend/src/pages/ChatPage.tsx` — "Recreate embeddings" button state.

## 4. Cancel an In-Progress Embedding Job

**Problem.** A started embedding job could not be stopped. If it was going to take too long, the only options were to wait it out or restart the backend.

**What changed.** Embedding jobs are now **interruptible**:

- A **Cancel** button appears in the shared progress modal whenever a job is running (on both the Search and Chat pages, since the modal is shared).
- Cancelling stops the work cooperatively at safe checkpoints: it skips the remaining URL downloads, stops between papers during embedding generation, and re-checks before building and saving the index.
- **No partial index is written.** The index and metadata files are only saved at the very end, after a final cancel check, so an existing index from a previous run is left untouched.
- The UI clears the progress modal immediately on cancel for instant feedback.

**Files:**
- `backend/app/api/routes/embeddings.py` — new `POST /embeddings/cancel` endpoint and a cooperative cancel flag passed into the job.
- `backend/app/services/embedding_service.py` — cancel checks threaded through extraction, processing, index build, and save.
- `frontend/src/services/api.ts` — `cancel()` API call.
- `frontend/src/context/EmbeddingContext.tsx` — `cancelEmbeddings()`.
- `frontend/src/components/EmbeddingProgressModal.tsx` — Cancel button for active jobs.

## New / Changed API Surface

| Method & Path | Change |
|---|---|
| `POST /embeddings/{filename}` | Now accepts an optional JSON body: `{ scrape_full_text?, max_scrape?, force? }` |
| `POST /embeddings/cancel` | **New** — cancels the in-flight embedding job |

## New Configuration Settings (backend)

| Setting | Default | Purpose |
|---|---|---|
| `SCRAPE_FULL_TEXT` | `true` | Whether to scrape paper URLs for full text by default |
| `SCRAPE_CONCURRENCY` | `10` | Max simultaneous downloads across all domains |
| `SCRAPE_TIMEOUT` | `10` | Per-request download timeout (seconds) |
| `SCRAPE_MAX_PAPERS` | `0` | Cap on number of URLs to scrape (`0` = no cap) |

---

## Notes & Current Limitations

- The full-text scraping **toggle and Recreate button currently live on the Chat page**. The Search page's "Create Embeddings" button still uses the default settings (full-text scrape) and does not force a rebuild.
- These changes affect only the embedding pipeline; search, analytics, and chat-response logic are unchanged.
- A separate, known issue (not addressed here) is the Gemini free-tier rate limit (5 requests/minute), which each chat turn can hit because it makes two model calls (query decomposition + answer).
