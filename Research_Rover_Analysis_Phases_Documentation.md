# Research Rover Analysis Feature - Phase Documentation

**Project:** Research Rover  
**Feature Area:** Metadata-driven analysis page  
**Date:** 2026-04-26

## 1. Purpose of This Document

This document explains the full set of phases that will be followed to build the new analysis area in Research Rover. The goal is to take the metadata already extracted by the platform and turn it into a dedicated analysis experience in the navbar.

The analysis page will focus on:

- keyword frequency
- keyword presence matrix
- keyword co-occurrence
- centrality calculations
- word cloud generation
- chart-based summaries

In simple terms, the process will transform raw research metadata into visual and mathematical insights.

## 2. Current Starting Point

Research Rover already has the core pieces needed for this feature:

- a search pipeline that extracts paper metadata
- a PubMed-based backend data source
- CSV output for paper records
- JSON mapping for full text
- a frontend route system with an existing `AnalyticsPage`
- a navbar that can be extended with a new analysis item

Relevant current files include:

- `backend/app/services/pubmed_service.py`
- `backend/app/services/search_service.py`
- `backend/app/models/schemas.py`
- `frontend/src/App.tsx`
- `frontend/src/components/layout/Navbar.tsx`
- `frontend/src/pages/SearchPage.tsx`
- `frontend/src/pages/AnalyticsPage.tsx`

The `keyword presence matrix` folder in the workspace is also conceptually related, because it already contains standalone scripts for matrix generation, word clouds, and centrality analysis.

## 3. Overall Workflow

The future analysis feature will follow this high-level flow:

1. Search papers in Research Rover.
2. Extract and normalize metadata.
3. Store the metadata in a structured format.
4. Aggregate keywords and related fields.
5. Generate analysis outputs.
6. Render those outputs on a new analysis page.
7. Allow the user to filter, compare, and export the results.

The important idea is that the analysis page should not depend on manual CSV work. It should read directly from the data generated by the Rover pipeline.

## 4. Phase 1 - Metadata Collection

### Goal

Collect clean paper metadata from the search pipeline so it can be used for analysis.

### What Happens

When the user runs a search, Research Rover gathers paper-level fields such as:

- title
- abstract
- authors
- DOI
- source
- publication year
- keywords
- citation information
- download URL

This already happens in the backend search flow, especially in:

- `backend/app/services/pubmed_service.py`
- `backend/app/services/search_service.py`

### Why This Phase Matters

All later analytics depend on this metadata. If the metadata is incomplete, the keyword counts and network metrics will also be incomplete.

### Output

A dataset of paper records that can be used as the input for keyword analysis.

## 5. Phase 2 - Metadata Normalization

### Goal

Make sure the extracted metadata is consistent and machine-readable.

### What Happens

The extracted data is normalized so that fields are stored in a standard way.

Examples:

- `DOI` and `Doi` are aligned
- `Source` and `Journal/Book` are aligned
- `Year_Published` and `Publication Year` are aligned
- keywords are converted into a clean list

This step is necessary because analysis logic works best when values have predictable names and formats.

### Why This Phase Matters

Without normalization, the same concept may appear under multiple field names, which would break counts and charts.

### Output

A clean metadata table ready for analytics.

## 6. Phase 3 - Data Storage for Analysis

### Goal

Store Rover metadata in a form that can be reused by the analysis page without re-running the search.

### What Happens

The analysis layer can read from one or more of these sources:

- CSV export from Rover search
- JSON full-text mapping
- a dedicated analysis cache or summary file

The key design choice is to keep analysis data separate from the raw search process.

### Recommended Storage Pattern

The following separation is ideal:

- CSV for searchable paper metadata
- JSON for full-text content
- JSON or database tables for precomputed analytics

### Why This Phase Matters

This makes the analysis page faster and easier to update later.

### Output

Reusable analysis-ready data source.

## 7. Phase 4 - Keyword Extraction and Aggregation

### Goal

Extract the meaningful keyword set from the paper metadata and measure how often each keyword appears.

### What Happens

The system will:

1. read the keyword lists from each paper
2. clean and normalize keyword spelling
3. merge aliases and abbreviations
4. count keyword frequency across all papers

This phase is conceptually similar to `keyword_presence_matrix.py`, which already normalizes keywords before building a matrix.

### Example Tasks

- convert `AI` to `artificial intelligence`
- convert `ML` to `machine learning`
- normalize spacing and punctuation
- remove duplicates inside a single paper

### Why This Phase Matters

This is the foundation of the frequency chart, word cloud, and presence matrix.

### Output

A keyword frequency table and a cleaned keyword vocabulary.

## 8. Phase 5 - Keyword Presence Matrix

### Goal

Represent which keywords appear in which papers.

### What Happens

A binary matrix is created:

- rows = papers
- columns = keywords
- cell value = `1` if the keyword appears in that paper, otherwise `0`

This is the same core idea used in the `keyword presence matrix` folder.

### Why This Phase Matters

The presence matrix is the base structure for:

- co-occurrence analysis
- graph building
- similarity analysis
- clustering

### Output

A binary matrix of keywords versus papers.

## 9. Phase 6 - Co-Occurrence Network Building

### Goal

Find which keywords appear together in the same paper.

### What Happens

If two keywords appear in one paper, an edge is added between them in a keyword network graph.

Example:

- if a paper contains `machine learning` and `healthcare`
- then the graph increases the weight of the edge between those two keywords

This is already reflected in the logic used by `graphnodes.py`.

### Why This Phase Matters

Co-occurrence shows how topics relate to each other and which themes are connected in the dataset.

### Output

A weighted keyword graph.

## 10. Phase 7 - Centrality Calculations

### Goal

Identify the most important keywords in the network.

### What Happens

The system calculates graph metrics such as:

- degree centrality
- closeness centrality
- betweenness centrality
- eigenvector centrality
- clustering coefficient

These calculations help identify:

- hub keywords
- bridge keywords
- tightly grouped themes

This phase is already represented in `graphnodes.py` and `centrality_plots.py`.

### Why This Phase Matters

Centrality gives the analysis page more than simple frequency counts. It shows importance in the network, not just repetition.

### Output

A centrality score table and ranked keyword lists.

## 11. Phase 8 - Visualization Layer

### Goal

Turn the analysis results into visual outputs that users can understand quickly.

### Visuals to Include

- keyword frequency bar chart
- word cloud
- keyword network graph
- centrality bar charts
- optional matrix heatmap

### Why This Phase Matters

The analysis page should help users spot patterns immediately, not force them to read raw tables.

### Output

A complete visual dashboard for keyword analysis.

## 12. Phase 9 - Frontend Analysis Page

### Goal

Display all analysis results in a clean and usable interface.

### What Happens

The frontend already has a route structure and a placeholder `AnalyticsPage`. The new analysis page can extend that route or replace it with a data-driven version.

The page can show:

- summary cards
- keyword chart
- word cloud
- co-occurrence graph
- centrality tables
- filters for source, date range, and filename

### Integration Points

- `frontend/src/App.tsx`
- `frontend/src/components/layout/Navbar.tsx`
- `frontend/src/pages/AnalyticsPage.tsx`

### Why This Phase Matters

This is the part users actually see and interact with.

### Output

A usable analysis dashboard in the navbar.

## 13. Phase 10 - Backend Analysis Endpoints

### Goal

Expose analysis data through the backend so the frontend can request it on demand.

### Possible Endpoints

- `GET /api/v1/analysis/summary`
- `GET /api/v1/analysis/keywords`
- `GET /api/v1/analysis/matrix`
- `GET /api/v1/analysis/network`
- `GET /api/v1/analysis/centrality`

### Why This Phase Matters

Backend endpoints make the analysis page reusable, scalable, and easier to maintain.

### Output

API responses containing charts, tables, and graph data.

## 14. Phase 11 - Filtering and Comparison

### Goal

Let the user compare analysis across different subsets of data.

### Filters That Can Be Added

- publication source
- date range
- specific CSV file
- search query
- keyword subset

### Why This Phase Matters

Research analysis is more useful when users can compare topics instead of only seeing one global summary.

### Output

Interactive filtered analysis views.

## 15. Phase 12 - Export and Reporting

### Goal

Allow the user to save analysis results.

### Possible Exports

- CSV for keyword frequency
- CSV for centrality scores
- PNG or SVG for charts
- PDF report for the analysis dashboard

### Why This Phase Matters

Users often need results for reports, thesis work, or presentations.

### Output

Downloadable analysis artifacts.

## 16. Phase 13 - Validation and Testing

### Goal

Make sure the analysis results are correct and stable.

### What Should Be Checked

- keyword normalization
- duplicate keyword handling
- matrix correctness
- graph edge weights
- centrality calculations
- frontend rendering

### Why This Phase Matters

Analytics features can look correct visually but still contain logical errors. Testing protects against that.

### Output

Verified and stable analysis logic.

## 17. Phase 14 - Optimization and Maintenance

### Goal

Keep the feature fast and maintainable as the dataset grows.

### Optimization Ideas

- cache analysis results
- recompute only when new data arrives
- avoid rebuilding large graphs unnecessarily
- store summary data separately from raw metadata

### Why This Phase Matters

Large metadata sets can become expensive to process repeatedly.

### Output

A faster and more sustainable analysis system.

## 18. Recommended Implementation Order

If this is built step by step, the best order is:

1. collect and normalize metadata
2. build keyword frequency counts
3. build the presence matrix
4. compute co-occurrence network data
5. compute centrality metrics
6. expose backend endpoints
7. build the frontend analysis page
8. add filters and exports
9. test and optimize

This order keeps the project practical because the visual page depends on the data logic underneath it.

## 19. How This Relates to the Existing Scripts Folder

The `keyword presence matrix` folder is a useful reference because it already contains the core logic for:

- normalizing keywords
- building the matrix
- charting keyword frequency
- plotting keyword networks
- calculating centrality
- generating a word cloud

In the new Rover analysis page, that logic should be moved from standalone scripts into reusable backend and frontend components.

## 20. Final Summary

The analysis feature can absolutely be built in Research Rover. The process should be split into clear phases:

- data extraction
- normalization
- storage
- keyword counting
- matrix building
- co-occurrence analysis
- centrality computation
- visualization
- frontend integration
- testing and optimization

That phased approach will make the feature easier to build, easier to debug, and easier to explain in your final project documentation.
